# 01: Keep credentials out of Keychain write-back failure records

**What to build:** When a write-back to a Keychain item fails, the error and
every log record it produces describe the failure without any part of the
credentials. Today, oc-auth passes a credential blob that's too long for the
`security` tool's interactive mode as a hex argument. If that process then fails
to start, or ends without an exit status, the platform error quotes the whole
command line. oc-auth keeps that text, so both `writeback_failed` debug records,
one per attempt, carry the complete hex-encoded credentials. Redaction can't
catch hex, so fix this where process failures become oc-auth errors. The review
reproduced this with synthetic credentials and a missing executable.

**Category:** bug

**Priority:** P1 (urgent)

**Where:** `packages/oc-auth/src/keychain-security.ts`,
`packages/oc-auth/src/keychain-items.ts`, and
`packages/oc-auth/src/claude-code-write-back.ts`.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] A Keychain write that passes the credentials as an argument, and then
      fails to start or ends without an exit status, produces no error or log
      record that contains any part of the credential blob, as text or hex.
- [ ] The failure is still reported, with a failure type that says what kind of
      process failure happened.
- [ ] Process failures are made safe where they become oc-auth errors, before
      their messages can reach write-back reporting. The fix does not depend on
      recognizing or redacting hex-encoded credentials in log records.
- [ ] Failed interactive-mode writes, and `security` runs that exit with an
      error status, keep their current reporting.
- [ ] A regression test uses synthetic credentials long enough to go in an
      argument, and a process failure whose message quotes the command line. It
      checks both write-back attempts and the resulting errors and captured log
      records for the blob, its token values, and their hex encodings. Both
      startup failure and termination without an exit status are covered.

### Triage Notes

**Verification:** Confirmed by inspection. The argv fallback for long blobs
passes the hex-encoded credentials as an argument; the process library's
platform error joins the command and its arguments into its message; the
`security` failure builder copies that message into both `message` and `stderr`;
write-back logs it in `writeback_failed` once per attempt; redaction only
recognizes `sk-ant-…` and JWT shapes, so hex passes through.

**Amendments:**

- Stream read failures on the argv run (stdout or stderr) produce the same
  command-line-quoting platform error. Cover them along with startup failure and
  termination without an exit status; a fix at the point where process failures
  become oc-auth errors covers all three.
- The comment on the `security` failure that says it never carries its arguments
  is false for this path; correct it with the fix.
- Write-back reporting most likely needs no change: the store error is caught
  inside write-through. The new failure-type names are the implementer's choice;
  update the documented values on the error type to match.
