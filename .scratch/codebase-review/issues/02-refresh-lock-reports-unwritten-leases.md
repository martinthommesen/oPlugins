# 02: Refresh lock reports a lease it couldn't write

**What to build:** Before oc-auth spends a refresh token, it extends its refresh
lock lease to cover the token request. If writing the extended lease fails, for
example with a disk error, the lock still reports success. The refresh goes
ahead while the lease on disk keeps its earlier, shorter expiry or is only
partly rewritten, so another OpenCode process can take the refresh lock and
refresh the same credential store at the same time. Two refreshes of one store
can sign Claude Code out. Deferring the lease into a cooldown has the same gap:
the lock counts it as a cooldown claim even when the write failed. Initial
publication uses the same write path. Make a lease count only once it's written.
The original review reproduced the extension case with an injected write
failure; initial publication and partial writes were found by reading the code.

**Category:** bug

**Priority:** P1 (urgent)

**Where:** `packages/oc-auth/src/refresh-lock-held.ts` and
`packages/oc-auth/src/credential-token-spend.ts`.

**Blocked by:** None (can start immediately)

**Coordinate with:** 03, for unreadable or partially written tickets and safe
warning fields. This is shared implementation work, not a prerequisite.

**Status:** ready-for-agent

- [ ] When writing an extended lease fails, extending reports failure and the
      refresh token isn't spent. The refresh waits for another process's result,
      as it does when the lock is lost.
- [ ] When writing a cooldown lease fails, the lock isn't marked as a cooldown
      claim. Releasing it follows the ordinary lease-expiry path rather than
      skipping the write because it thinks the lease was deferred.
- [ ] A failed initial lease publication never reports a successfully
      coordinated lock. Document its outcome separately from the existing,
      explicitly warned degraded mode for an unusable lock directory.
- [ ] These outcomes hold when a write changes some bytes before failing, not
      only when it fails before writing anything. A partial write is not assumed
      to leave the old lease intact.
- [ ] A failed lease write is logged: a warning with metadata only, and the
      error in a debug record. Credential-store paths never go in the warning.
- [ ] The comments on the lease format stop promising that a failed write leaves
      the previous lease in force, and say what the fixed-width format does and
      doesn't guarantee.
- [ ] Regression tests inject failures before writing and after writing some
      bytes, covering initial publication, extension, and deferral. They check
      the reported outcome, the absence of token spending after failed
      extension, and ordinary release after failed deferral.

### Triage Notes

**Verification:** Confirmed by inspection. Writing a lease catches every
platform error, logs it at debug level only, and returns success. Extension
reports `true` regardless; deferral marks the lock as a cooldown claim before
the write; initial publication ignores failure. The lease-format comments
promise that a failed write leaves the previous lease in force.

**Amendments:**

- The token-spend side already waits for another process when extension reports
  failure (pinned by the existing "waits for the lock holder's credential when
  the lease is lost" test), so the fix belongs in the held lock; token spending
  most likely needs no change.
- A failed _initial_ publication that wrote nothing leaves an empty ticket,
  which readers already treat as live for their own TTL. The real risk there is
  a partial write or a reader with a shorter TTL. The implementer chooses
  whether a failed publication waits (`Busy`) or continues in a warned degraded
  mode, and documents it against the existing lock policy that refusing to
  refresh is worse than a degraded lock.
- The lock only receives the credential source key, which for a credentials file
  is `file:<config dir>`. The warning must name the store without that path;
  choose one path-free identifier and use it in both this ticket and 03.
- Add the new warning to the oc-auth README's log table.

**Sequencing:** 03 edits the same held-lock code and test support. Do 02 and 03
in sequence or together.
