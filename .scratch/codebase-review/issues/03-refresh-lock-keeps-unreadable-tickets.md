# 03: Refresh lock never shortens or drops a ticket it can't read

**What to build:** Each OpenCode process that wants to refresh a credential
store claims the refresh lock with a ticket file, whose lease says when the
claim ends. When oc-auth can't read another process's ticket for any reason
other than the ticket being gone, it assumes the claim ends one default lease
length after the ticket last changed, which can be sooner than the lease written
in it. When it can't examine a ticket at all, it ignores the claim. Either way,
two processes can refresh one store at once, and nothing in the log shows that
the refresh lock has a problem. Make sure a ticket that exists but can't be read
never weakens the lock without a warning.

The `refresh_lock_degraded` warning also carries a path: for a credentials file,
it names the store by its config directory. Warnings carry metadata only, so
name the store without the path.

The review found both by reading the code. Neither was reproduced.

**Category:** bug

**Priority:** P1 (urgent)

**Where:** `packages/oc-auth/src/refresh-lock-ticket-files.ts`,
`packages/oc-auth/src/refresh-lock.ts`, and
`packages/oc-auth/src/refresh-lock-held.ts`.

**Blocked by:** None (can start immediately)

**Coordinate with:** 02, for failed lease publication and partial writes. This
is shared implementation work, not a prerequisite.

**Status:** ready-for-agent

- [ ] A ticket that exists but can't be read never counts as ending sooner than
      the lease it can hold. Choose and document the rule. If it uses a duration
      after the ticket last changed, that duration covers every lease oc-auth
      can write: initial leases, token-request extensions, and cooldowns,
      including leases from another process with different options. The reader's
      configured TTL is not a bound on another process's lease.
- [ ] A ticket that can't be examined is never silently treated as absent:
      oc-auth either waits for it or takes the documented degraded path, with
      its warning.
- [ ] A ticket that has disappeared, and a new ticket that is read successfully
      and is empty before its first lease, keep their current handling. A
      malformed or partly written nonempty lease is handled conservatively, not
      mistaken for an empty new ticket.
- [ ] `refresh_lock_degraded` warnings name the credential store without a path.
      The path goes only in the debug record.
- [ ] Failing to remove an expired ticket, for a reason other than it being
      gone, is logged in a debug record.
- [ ] Regression tests cover unreadable extended and cooldown leases, a longer
      initial lease written by a process with different options, a ticket that
      can't be examined, a partially written lease, and the warning's fields.

### Triage Notes

**Verification:** Confirmed by inspection. A read or decode failure becomes "no
lease", and the fallback expiry is the ticket's mtime plus the _reader's_
configured TTL (default 20 s), shorter than extension (45 s) and cooldown (up to
60 s) leases. A failed `stat` drops the claim silently. A partly written lease
is treated like an empty new ticket. Failed removal of an expired ticket is
ignored. `refresh_lock_degraded` carries the source key, which contains the
config directory, contrary to the README's "never a path".

**Amendments:**

- The body's "one default lease length" is the reader's configured TTL; the
  acceptance criteria already say this correctly.
- A conservative rule needs a bound so a permanently unreadable foreign ticket
  can't stall refreshes forever. The longest lease oc-auth can write is the
  lock's maximum TTL (120 s); document whatever bound is chosen.
- Use the same path-free store identifier chosen for 02; the lock only receives
  the source key.
- Update the README's log table if warning fields change.

**Sequencing:** shares the held-lock code and test support with 02. Do them in
sequence or together.
