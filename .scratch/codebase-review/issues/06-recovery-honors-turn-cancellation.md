# 06: Unauthorized recovery honors turn cancellation

**What to build:** After a 401, unauthorized recovery adopts or refreshes the
credential and sends the request again. That request carries oc-auth's own
cancellation signal instead of the turn's, and recovery checks the turn's signal
only before it starts. If the user cancels the turn after recovery starts, the
request still goes out, and its response body keeps streaming. Make cancelling
the turn stop recovery's request at every stage. The review reproduced this
against a local server: after the cancellation, the body still delivered all of
its data.

The shared credential refresh is different from a model-request replay. Its
leader deliberately outlives an individual caller, so a cancelled caller does
not strand a rotated token or cancel a refresh another caller is awaiting.

**Category:** bug

**Priority:** P2 (normal)

**Where:** `packages/oc-auth/src/anthropic-fetch.ts`,
`packages/oc-auth/src/unauthorized-recovery.ts`, and
`packages/oc-auth/src/credential-refresh.ts`.

**Blocked by:** None (can start immediately)

**Coordinate with:** 07 for response cleanup and 18 for failure reporting.

**Status:** ready-for-agent

- [ ] Cancelling the turn before recovery sends the request again keeps it from
      going out, including when cancellation happens while this caller awaits
      adoption or a shared refresh result.
- [ ] Cancelling the turn while recovery waits for the response aborts the
      request.
- [ ] Cancelling the turn while the response body streams stops the body.
- [ ] Interrupting recovery itself still aborts its request, as today.
- [ ] Cancelling one caller's turn stops that caller's recovery work without
      cancelling the shared refresh leader or its write-back, or other callers
      awaiting its result. Plugin-scope shutdown remains a separate lifecycle.
- [ ] Expected turn cancellation is not reported as a failed send or an
      unexpected recovery error.
- [ ] Regression tests cover each case with an injected fetch or a local server,
      and the existing test for a turn cancelled before the 401 still passes. A
      shared-refresh test verifies that another caller still receives the result
      and that refreshed credentials are written back.

### Triage Notes

**Verification:** Confirmed by inspection. The turn's signal is checked once,
before recovery starts. The replay is rebuilt with the turn's signal, but the
fetch call then passes Effect's own interruption signal in its init, which
replaces the request's signal, so the turn's cancellation is lost. Nothing races
the turn's signal against adoption or refresh waits.

**Amendments:**

- The shared refresh leader is already forked into the service scope and joiners
  only await its result, so "don't cancel the leader" already holds; it needs a
  regression test, and the credential-refresh code most likely needs no change.
- When the turn is cancelled mid-recovery, the hook returns the original 401, as
  the existing test for cancellation before recovery expects. It must not
  surface as a fetch error that falls into the failed-recovery path.

**Sequencing:** 06, 07 and 18 all change the same recovery function. Do 07, then
06, then 18.
