# 10: Keep Claude subscription requirements in advisor consultations

**What to build:** When an advisor consultation uses an Anthropic model with a
Claude subscription, oc-auth replaces the consultation's system prompt with the
billing header and Claude Code's identity, which subscription requests need.
oc-advisor then replaces the system prompt of the consultation session with the
advisor's instructions. Hooks run in plugin order, so when oc-auth is listed
before oc-advisor, the billing header and identity are gone before the request
is sent. The review reproduced this by running both plugins' hooks in that
order. It didn't test how Anthropic answers such a request. oc-advisor's
consultation hook also has no tests. Make consultations keep both the
subscription requirements and the advisor's instructions, whichever plugin loads
first.

oc-auth normally relocates non-billing system instructions into the first user
message. The advisor's instructions must survive in the effective request; they
need not remain in the system prompt. Both plugin orders are required, not an
order restriction documented as a workaround.

**Category:** bug

**Priority:** P2 (normal)

**Where:** `packages/oc-advisor/src/hooks.ts`,
`packages/oc-advisor/src/hooks.test.ts`, and
`packages/oc-auth/src/session-context.ts`.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] oc-advisor has tests of its own for its consultation hook: consultation

## Agent Brief

**Category:** bug **Summary:** Run consultations as a hidden consultation agent
so Claude subscription requirements survive whichever plugin loads first.

**Current behavior:** oc-advisor registers a `generate` session hook that, for
consultation sessions, replaces the whole system prompt with the advisor's
instructions and removes the tools. oc-auth's Anthropic `generate` hook sets the
system prompt to the billing header plus Claude Code's identity and relocates
other system text into the first user message. The host runs `generate` hooks in
plugin load order, with no priority option, so when oc-auth loads first
oc-advisor wipes the billing header and identity.

**Desired behavior:**

- oc-advisor registers a **consultation agent** through the host's agent editor
  (`ctx.agent` transform, `update(id, draft => …)`): a reserved ID in
  oc-advisor's namespace. Because `update` edits an existing agent of the same
  ID, oc-advisor sets every field it relies on rather than trusting what's
  there, and documents the reserved ID. It also sets `mode: "primary"` (so the
  subagent tool refuses it), `hidden: true`, `system` set to the advisor's
  instructions, and permissions ending in a deny-all rule (`action "*"`,
  `resource "*"`, `effect "deny"`), as the host's built-in `title` and `summary`
  agents do.
- Every consultation session is created with that agent
  (`SessionCreateInput.agent`). The host then builds the agent's prompt into the
  request before any `generate` hook runs, so oc-auth's hook sees it, keeps the
  billing header and identity, and relocates the advisor's instructions, in
  either plugin order.
- oc-advisor no longer registers a consultation `generate` hook. Its other
  session hooks (presenting the advisor) are unchanged.
- The consultation still offers no tools: the effective permissions (agent rules
  merged with session rules) deny every tool, including code mode's `execute`.
- The README describes what a consultation now sees: the advisor's instructions
  plus the session's usual instruction text, the conversation transcript, and no
  tools. It no longer says the plugin replaces the consultation session's system
  prompt or that the advisor doesn't see instruction files.

**Key interfaces:**

- The host's agent editor (`AgentDomain.transform` / `AgentEditor.update`) and
  `Agent.Info` fields `system`, `mode`, `hidden`, `permissions`.
- `SessionCreateInput.agent` on the session create call oc-advisor's host
  adapter makes for a consultation.
- The layout check's suppression rules and the root `AGENTS.md`: the
  `typescript/prefer-readonly-parameter-types` suppression on a host editor's
  draft parameter becomes allowed in a named list of files, oc-auth's model
  pricing and oc-advisor's agent registration, written exactly as the existing
  one. No other suppression is added and the rule's severity is unchanged.

**Acceptance criteria:**

- [ ] Setup registers the consultation agent with its reserved ID, primary mode,
      hidden, the advisor's instructions as `system`, and a final deny-all
      permission rule. A test captures the registration through a fake host
      agent editor and checks each field.
- [ ] Every consultation session is created with the consultation agent's ID. A
      test checks the create call, and that the session's own permissions don't
      re-allow any tool after the agent's deny-all rule (session rules are
      evaluated after the agent's).
- [ ] Registering over an existing agent with the reserved ID still yields every
      field above. A test starts from a draft with conflicting values.
- [ ] oc-advisor registers no `generate` hook. A test fails if one is
      registered.
- [ ] Sessions that aren't consultations are unaffected: no agent is forced on
      them, and their system prompts, messages, and tools are not touched by
      oc-advisor.
- [ ] oc-auth has a test that a `generate` event whose system prompt is foreign
      text it didn't write (shaped like the advisor's instructions, plus a
      second instruction part) ends with the billing header and identity as the
      system prompt and that text in the first user message.
- [ ] The layout check allows the draft suppression in exactly the two named
      files and still rejects it elsewhere; its tests cover both. `AGENTS.md`
      names both files.
- [ ] oc-advisor's README is updated as described, and the glossary's
      **Consultation agent** term is used in docs and code comments.
- [ ] `pnpm run check` passes.

**Out of scope:**

- Suppressing the session's inherited instruction text in consultations.
- Any change to oc-auth's subscription rewrite beyond the new test.
- Failure categories for availability checks and cleanup (ticket 20), which
  edits the same hooks file: coordinate to avoid merge conflicts.
- A cross-plugin integration test or a layout-policy change to allow one.
