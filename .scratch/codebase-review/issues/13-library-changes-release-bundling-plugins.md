# 13: A library change releases every plugin that bundles it

**What to build:** Production libraries are built into each plugin that uses
them and are never released on their own. The release configuration lists only
plugin directories, and release-please ignores commits that touch only other
paths. A fix that changes only a library therefore releases no plugin, and every
plugin that bundles the library keeps shipping the defect until an unrelated
change to that plugin triggers a release. The review confirmed the path
filtering in release-please 17.6.0, the version in the current
`release-please-action@v5` lockfile, against this repository's configuration. It
did not run a release-generation test. Make a library change release each plugin
that bundles it.

Both bundled libraries and test-only libraries are declared as
`devDependencies`, so that field alone does not identify release consumers.
Currently, `log-redaction` is bundled by oc-auth and oc-auto, and
`plugin-options` by all four plugins. `captured-logs` and `host-test` are
test-only and are not bundled into any plugin.

**Category:** bug

**Priority:** P2 (normal)

**Where:** `release-please-config.json`, `.github/workflows/release.yml`, plugin
`package.json` and `tsdown.config.ts` files, and the root `README.md`.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

**Superseded:** the Agent Brief under Comments replaces the acceptance criteria
below and the earlier `ready-for-human` triage notes, which are kept as history.

- [ ] A `fix` or `feat` commit that touches only a library opens a release pull
      request for every plugin that bundles the library, and for no other
      plugin.
- [ ] A commit that changes only a test-only library does not release plugins.
      Classifying a dependency as bundled is not based on `dependencies` versus
      `devDependencies`; it reflects the code included in published bundles.
- [ ] Which plugins a library change releases follows the plugins' declared
      library dependencies and their production use, including transitive
      bundled dependencies. A check fails when the release mapping and those
      consumers drift apart.
- [ ] The README's Releasing section says how a library change is released.
- [ ] A release-please dry run or release-generation test, using the version
      selected by the release action, shows that a synthetic library-only commit
      reaches the affected plugins' release candidates. A mapping-unit test
      alone is not sufficient. Cover multiple consumers, an unaffected plugin,
      and a test-only library without creating real releases or pull requests.

**Verification:** Confirmed for this repository: the release config lists only

**Why ready-for-human:** release-please can't express "this library's changes
release these plugins". Its `additional-paths` option is still an open, unmerged
pull request (googleapis/release-please#2534), and the `node-workspace` plugin
would publish libraries, which ADR 0002 rules out. The maintainer must choose a
mechanism, for example:

- a CI step that maps library-only commits to the plugins that bundle them and
  triggers their releases;
- a rule, enforced by a check, that a library fix also touches its consuming
  plugins;
- different release tooling.

The release-generation criterion also needs a GitHub token and a pushed commit
for a release-please dry run, or a new dev dependency to run it against a
stubbed GitHub; both are maintainer decisions.

**Agent-ready once decided:** the drift check (it belongs with the existing
release rules in `tools/` and can use the layout snapshot) and the README's
Releasing section. `release.yml`, the plugins' `package.json` files and
`tsdown.config.ts` most likely need no change, whichever mechanism is chosen.

## Agent Brief

**Category:** bug **Summary:** A library change releases exactly the plugins
it's bundled into, through a per-plugin fingerprint that release-please sees as
a change in each plugin's folder.

**Current behavior:** release-please (17.6.0, the version
`release-please-action@v5` bundles) assigns a commit to every configured package
whose folder one of its files falls under, and ignores files outside those
folders. Only plugin folders are configured, so a commit that touches only a
library releases no plugin.

**Desired behavior:**

- Each plugin commits a fingerprint file inside its own folder: a deterministic
  digest of the source and build inputs of every library bundled into it,
  including libraries those libraries bundle, and never test-only code or a
  library the plugin uses only in tests. Bundling follows the plugin's
  production imports, not whether a library is listed under `dependencies` or
  `devDependencies`. The built bundle is not hashed.
- A repository command regenerates every fingerprint. The pre-commit hook runs
  it against the staged snapshot and stages only the regenerated fingerprint
  files, never unrelated working-tree edits.
- `pnpm run check` (through the layout check or a sibling check in `tools/`)
  fails when any fingerprint is stale, naming the plugin and the command that
  fixes it.
- The release workflow runs that check before release-please, and release-please
  doesn't run if it fails. The check must validate the revision release-please
  actually processes. release-please reads the head of `main` when it runs, not
  the commit that triggered the workflow, so if `main` has moved past the
  validated commit the run skips release-please and leaves the release to the
  newer push's run.
- The fingerprint decides which plugins a change affects; the commit type still
  decides whether anything releases. A library `fix:` releases the plugins it's
  bundled into; a library `chore:` or `refactor:` releases nothing. A commit
  that only repairs a stale fingerprint must carry `fix:`/`feat:` itself to
  release the change, with the significance the library change needed, including
  a breaking-change marker.
- The README's Releasing section explains all of this, including the repair
  case, and links ADR 0004.

**Key interfaces:**

- `release-please-config.json` stays limited to plugins. No libraries are added
  as release-please packages and the `node-workspace` plugin isn't used.
- The release workflow's job graph: a fingerprint-check job that release-please
  depends on.
- The existing release rules in `tools/` and the layout snapshot, for reading
  plugin imports and library sources.
- release-please's exported `Manifest`, which accepts any source-control backend
  (its `Scm` interface is not re-exported and has to be imported from its
  internal path).

**Acceptance criteria:**

- [ ] Every plugin has a fingerprint file, and the regeneration command
      reproduces it byte for byte on a clean checkout.
- [ ] Changing a bundled library's source makes the check fail for exactly the
      plugins it's bundled into. Changing a test-only library, or a library's
      tests, changes no fingerprint. Tests cover a library bundled into several
      plugins, a plugin that doesn't bundle it, a test-only library, and a
      library pulled in through another bundled library.
- [ ] The pre-commit hook regenerates and stages fingerprints from the staged
      snapshot. A test or documented manual check shows unstaged library edits
      don't leak into the staged fingerprint.
- [ ] The release workflow's fingerprint check runs before release-please and
      blocks it on failure, and release-please is skipped when `main` has moved
      past the validated commit.
- [ ] release-please is pinned in `tools/` at the version the release action
      bundles, and a check fails when the two differ.
- [ ] An offline test runs release-please's release-PR planning against a fake
      source-control backend with synthetic commits. It shows: a library `fix:`
      with updated fingerprints releases exactly the plugins it's bundled into;
      a test-only library change releases none; `fix`/`feat`/breaking
      classification carries through to version bumps; unrelated plugins are
      untouched; and a `chore:` fingerprint repair alone releases nothing. It
      creates no real releases or pull requests and needs no token or network.
      This harness is untried: if release-please's planning can't be driven
      offline at the pinned version, stop and report back rather than weakening
      the criterion.
- [ ] The README's Releasing section and ADR 0004 agree with the implementation.
- [ ] `pnpm run check`, `knip`, and `sherif` pass with the new dev dependency.

**Out of scope:**

- Requiring pull requests or branch protection on `main`.
- Moving to changesets, the `additional-paths` fork, or `node-workspace`.
- Publishing libraries or giving them versions, changelogs, or tags.
- Changing what the publish jobs do after release-please.
