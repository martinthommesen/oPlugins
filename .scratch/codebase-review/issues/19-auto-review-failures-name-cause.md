# 19: Auto-review failure records name their cause

**What to build:** When a request to the reviewer fails, oc-auto gives the
permission prompt an `ask` verdict and logs `auto_review_failed` with only the
model and the step that failed. It drops the underlying cause, such as an HTTP
status, a network error, or a response stream that ended early, and the `ask`
message names only the step. Failed calls to the host are reported the same way.
Neither users nor maintainers can tell a rate limit from an outage or a broken
stream. The review found this by reading the code. Name a safe category for the
cause in the warning and the message.

**Category:** enhancement

**Priority:** P3 (follow-up)

**Where:** `packages/oc-auto/src/review-failure.ts`,
`packages/oc-auto/src/request-failed-error.ts`,
`packages/oc-auto/src/responses-stream.ts`, and
`packages/oc-auto/src/host-error.ts`.

**Blocked by:** None (can start immediately)

**Coordinate with:** 14, so the registered-hook tests exercise the same failure
reporting. Neither ticket needs to wait for the other.

**Status:** ready-for-agent

- [ ] A failed review request logs `auto_review_failed` with a safe category for
      the cause, such as the HTTP status, a network error, or an incomplete
      stream.
- [ ] The `ask` message gives guidance that matches the category, such as
      waiting after a rate limit.
- [ ] Failed host calls carry a category where the host's error provides one.
- [ ] Categories come from a documented, bounded vocabulary, with an `unknown`
      fallback and a numeric HTTP status where available. Classification uses
      structured failures or known local failure reasons, not matching arbitrary
      provider or host error messages. Stream failure sites retain enough safe
      information to distinguish incomplete output from other stream failures.
- [ ] No record carries the provider's error text, response bodies, or
      transcript content.
- [ ] Every failure still ends in an `ask` verdict, each new failure category
      has a test that expects it, and the README's log table lists the new
      fields. Tests also cover the `unknown` fallback and inject sensitive
      provider or host text to verify it appears in neither records nor the
      user-facing message.
