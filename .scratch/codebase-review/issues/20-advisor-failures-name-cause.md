# 20: Advisor failure records name their cause

**What to build:** oc-advisor reports a failed host call by the name of the
failed operation alone. Failed consultations, failed availability checks that
hide the advisor, and failed cleanups of consultation sessions log only which
operation failed or which session was involved. When `/advisor` can't list
models, it tells the user but logs nothing, and a cleanup warning can't tell a
timeout from exhausted retries. The review found this by reading the code. Log a
safe category for each of these failures.

**Category:** enhancement

**Priority:** P3 (follow-up)

**Where:** `packages/oc-advisor/src/host.ts`,
`packages/oc-advisor/src/hooks.ts`, `packages/oc-advisor/src/tool.ts`, and
`packages/oc-advisor/src/command.ts`.

**Blocked by:** None (can start immediately)

**Coordinate with:** 10, which edits the same oc-advisor hooks file. This is a
merge risk, not a prerequisite.

**Status:** ready-for-agent

- [ ] Failed consultations, availability checks, and model listings log a
      warning with a safe category, such as a timeout or a missing session,
      where the host's error provides one.
- [ ] A failed model listing for `/advisor` is logged, not only shown to the
      user.
- [ ] A failed consultation session cleanup says whether it timed out or ran out

- [ ] Categories come from a documented, bounded vocabulary with an `unknown`

- [ ] Existing behavior is preserved: failed availability checks hide the

- [ ] The README's log table lists the new records and fields.

### Triage Notes

**Verification:** Confirmed by inspection. Host failures are logged with only
the operation; availability checks log only the operation and session; cleanup
logs only the session, though a deadline (`Cause.TimeoutError`) and exhausted
retries are distinguishable; a failed `/advisor` model listing logs nothing.

**Amendments:**

- Consultation timeouts and invalid models already log useful fields; the gap is
  host failures. Host categories mean outcomes such as not found, unauthorized,
  or unavailable, not a timeout. Like 19, the host types declare failures as
  `unknown`, so `unknown` is acceptable when nothing structured arrives.
- Log tests need `@oc-lib/captured-logs` as a dev dependency, and the fake host
  needs a failing model listing. Classify raw host errors at the real host
  adapter, which is where they become `HostError`.

**Sequencing:** 10 edits the consultation hook in the same hooks file and its
tests; this ticket edits the availability hook there. It's a merge risk, not a
blocker.
